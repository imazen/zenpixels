# Foundation and compatibility assessment

**Current design draft:** see
[API/contract proposal for 0.2 and 0.3.1](api-contract-proposal-0.2-and-0.3.1.md).
The owner selected same-source compatibility with one zenpixels version per
connected pipeline. Shared type definitions across simultaneously loaded minor
versions are not required. That decision supersedes the facade/shared-package
alternatives below; their experiments remain historical evidence only.

**Release decision correction, 2026-09-27:** target a 0.2 migration release
followed by **0.3.1**, not an additional 0.4 release. The owner reports that
0.3.0 was accidentally published and yanked seconds afterward. Its publication
still exists, but it was not intended as a supported consumer target.

The published dependency concern was checked against crates.io's
[zenpixels reverse-dependency API](https://crates.io/api/v1/crates/zenpixels/reverse_dependencies?page=1&per_page=100)
and [zenpixels-convert reverse-dependency API](https://crates.io/api/v1/crates/zenpixels-convert/reverse_dependencies?page=1&per_page=100).
All 23 returned zenpixels dependent versions use `^0.2.x`; all five returned
convert dependent versions also use `^0.2.x`. The patch floors differ, so they
are not literally all `^0.2.2`. In particular, published zenpixels-convert
0.2.16 requires zenpixels `^0.2.16`, unlike the wide requirement in the local
workspace. None of these returned published requirements admits 0.3.1. This
checks the versions returned by the reverse-dependency endpoints, not every
historical version of every dependent.

The earlier inference that the local wide ranges were already published was
incorrect. Their presence creates a check before the next publish, not evidence
of existing published exposure. Consumers should opt in to a tested range only
after migrating to the common nondeprecated API. The supported source matrix
is the designated 0.2 bridge patch and 0.3.1. Changes without deprecation
warnings need explicit compatibility treatment; mixed-version type identity
remains a separate integration gate.

The exploration below retains its original 0.4 labels and three-version
prototype as historical design/evidence. Those labels do not prescribe another
release or a requirement to support three release lines; this correction
supersedes that numbering and rollout scope.

2026-09-27. Assessment of `main` at `17c78d9`, with both packages declaring
0.2.16. This is a proposed direction, not an implemented release contract.
The existing foundation review and 0.2.17/0.3.1 plan were inputs; their full
defect suites and ecosystem audits were not rerun. Existing uncommitted review
files were left intact.

**Revised recommendation following owner clarification:** use the present
controlled-ecosystem migration window to establish the desired 0.4 contracts
before more crates publish against today's API. The owner reports 23 published
crates and approximately 60 soon; these are planning inputs, not counts
independently verified in this assessment. Design the destination first and
coordinate consumer migration. Preserve source portability through a defined
bridge API, rather than making the whole legacy surface permanent merely to
preserve type identity.

Preserve the existing separation between interchange and conversion, and spend
the breaking-change budget on enforceable semantics and predictable execution
costs. Source compatibility, type identity, and semantic compatibility are
separate release requirements. The re-export prototype below remains useful,
but sharing the entire current implementation is now a fallback, not the
preferred destination.

## 0. Use the migration window deliberately

The earlier recommendation overweighted the cost of updating consumers relative
to the long-term cost of preserving today's public contracts. A controlled
rollout makes meaningful breaks practical now. It does not make already
published artifacts mutable or automatically migrate third-party applications.

Settle these contracts before choosing what gets backported:

- Validated descriptors and storage, with private invariant-bearing fields
  where warranted. The old writable descriptor need not remain the canonical
  0.4 type. Keep a separate raw description only if an actual caller needs it.
- Borrowed pixels with borrowed current-color information; ownership of color
  metadata at image/plan boundaries. Reconsider the view representation now
  rather than requiring every future borrow to preserve an Arc-owning design.
- One authoritative current encoding, explicit original signaling, and valid
  HDR units. Resolve conflicts explicitly before execution.
- Complete conversion plans, independently owned workers, explicit preparation
  and fallible execution where backends can fail. Replace misleading Clone or
  composition contracts rather than preserving them for convenience.
- Complete ownership extraction/adoption so pooling and any migration adapters
  preserve offsets, strides, interpretation and allocation ownership.

Prototype these contracts through zencodec and representative RGB8, high-depth,
planar and HDR/CMS consumers before freezing them. Their real call sites should
determine whether the design is easier to use. Then migrate the ecosystem in
dependency order: shared interchange and integration traits, codec adapters,
processing libraries, then applications. Move not-yet-published crates onto the
destination API before their initial release where practical.

The compatibility promise should be: **migrated consumer source uses one
documented API available on the supported bridge patches and 0.4.** It should
not promise unchanged support for every historical 0.2 API.

For source portability alone, backport that API and compile the same consumers
against each supported line. For simultaneous exchange of redesigned types
between different release lines, expose the new definitions under an additive
common module path in the old lines and the same path in 0.4. A semantic module
name such as `pixels` is illustrative, not a selected public API:

```text
0.2.B legacy root types ── explicit adapters ── new carrier definitions
0.2.B::pixels ─┐                                      ↑
0.3.C::pixels ─┼──────────── re-export ─────────────────┘
0.4.x::pixels ┘
```

New callers can use the same imports on all supported lines. Old root types
may remain in 0.2 for old source; they do not become identical to redesigned
types. Migrate a codec's public signatures deliberately, and version that codec
appropriately if the types change. Prefer whole-pipeline migration over adding
adapters between every stage. Zero-copy adapters are conditional on compatible
storage ownership and complete metadata extraction, not a universal promise.

The new definitions could live in the destination core with old lines depending
on it, or in a small shared package. Select that packaging after the contracts,
MSRV and dependency graph are proven; do not commit the current API to a new
1.0 package first. A conventional bridge depending on 0.4 is published after
0.4; an independently published shared package allows the bridge to precede it.
Keep the graph acyclic and account for feature unification.

Do not make 0.3 a separate redesign simply to visit the next version number.
If it must be supported, give it the same migration surface. Coordinate one
destination design, backport the common API, and publish the supported release
lines in dependency order. Existing `<0.4` requirements still need deliberate
updates before consumers can resolve directly to 0.4.

Dependency ownership also makes upstream compile-time improvements practical.
Measure and fix duplicated macro work, excessive generic expansion and default
features in the owned dependency crates themselves. The measurements in this
document identify candidates, not proof that any dependency can be removed
without replacing useful behavior or changing the safety policy.

## 1. What is already sound, and what needs work

The core/conversion split is valuable. `zenpixels` already excludes SIMD,
CMS execution, conversion planning and perceptual ranking dependencies. Its
normal dependencies are bytemuck and whereat. Keep that boundary. Pixel
interchange must not require compiling a conversion engine.

The storage model is also useful: `PixelBuffer`, `PixelSlice`, `PixelSliceMut`,
and `PixelCow` express ownership directly, while `P = ()` permits dynamic
formats. Preserve familiar names and the typed/erased relationship.

Current source exposes several costs and contract weaknesses:

| Finding checked in current source | Consequence | Direction |
|---|---|---|
| `PixelSlice` stores `Option<Arc<ColorContext>>`; `PixelBuffer::as_slice`, slice cloning and subviews clone it (`buffer.rs:324,2479`) | A metadata-bearing borrow performs reference-count work | Borrow context for ordinary views; own/share it at ownership boundaries |
| `with_icc`, `with_cicp`, `with_diffuse_white` rebuild an Arc-wrapped context (`buffer.rs:556`) | Chained metadata attachment can allocate repeatedly | Build current color once and attach once; keep convenience wrappers outside hot loops |
| `PixelDescriptor` has writable public fields (`descriptor.rs:631`) | It cannot be treated as proof that an encoding is valid | Establish a checked 0.4 representation; validate legacy inputs at migration boundaries |
| `reinterpret` checks bytes per pixel and returns `Self` (`buffer.rs:473`) | Alignment and the typed pixel marker can disagree with the new descriptor | Revalidate; layout changes need explicit erasure/retyping |
| `ColorContext::as_profile_source` prefers ICC, while `transfer_function` and `is_srgb` inspect CICP (`color.rs:401`) | Different helpers can interpret the same pixels differently | Resolve current interpretation once; keep original signaling separately |
| Owned external CMS uses `Arc<Mutex<_>>`; `convert_row` locks it (`converter.rs:32,289`) | Per-row synchronization and contention between cloned workers | Independent mutable execution state per worker |
| `RowConverter::compose` reconstructs from the descriptor plan; no_std clone drops an owned external transform (`converter.rs:373,389`) | Plans and clones do not reliably preserve behavior | Complete executable plans; explicit fallible worker creation |
| Scratch starts empty and grows during execution (`convert.rs:1990`) | “Preallocated” does not mean the first row is allocation-free | Preparation for a width reserves required scratch and prepares lazy kernel state |
| Five POD types derive bytemuck traits (`buffer.rs`, `pixel_types.rs`) | Even minimal core builds compile a proc-macro chain | Measure and address the derive dependency without casually abandoning safety policy |

The foundation review supplies additional reproduced correctness cases: alpha
omitted from finalizer identity checks, incorrect ICC forwarding, lossy
composition cancellation, HDR scale confusion, and metadata loss through some
ownership/orientation paths. These remain acceptance criteria, not claims that
this assessment reran every reproduction.

One documentation discrepancy was independently visible: crate-level allocation
docs promise that infallible construction uses a single calloc-like path, but
`PixelBuffer::new` currently calls `try_new(...).expect(...)`, whose allocation
uses reserve and resize. Do not use the existing prose as performance evidence.

## 2. The API that callers should learn

Keep the basic vocabulary small:

1. A descriptor describes physical layout and declared sample interpretation.
2. A buffer owns pixels; views borrow them; a cow represents a conditional copy.
3. Current color describes the pixels now. Origin metadata describes their history.
4. A conversion plan resolves meaning, policy and backend feasibility.
5. A prepared worker executes that plan with explicit output ownership.

Use the same vocabulary across buffered, row/strip and planar paths. Preserve
this crate's byte-stride convention and native-endian sample contract; spell
units in parameter names and documentation. A version transition must not
silently reinterpret the same stride integer as pixels instead of bytes.

Recommend one construction/planning path in docs, with three execution forms:
caller-provided output, consuming/reusing owned storage, and allocating output
when requested. Keep a clearly documented borrow-or-own identity path. A
caller-output identity operation necessarily copies; it must not be described
as zero-copy.

Do not reproduce every operation as a free function, several extension traits,
and several buffer methods just for symmetry. Keep old wrappers when needed
for compatibility, but concentrate examples and navigation on the preferred
route. Pure mathematical functions can remain free functions. Receiver methods
are useful when the receiver owns meaningful state or resources.

Avoid a public generic parameter for every color, policy, CPU and backend
combination. Retain the useful pixel-layout parameter, erase to a common
non-generic implementation early, and make wrappers small. This limits
monomorphization and keeps error messages readable. An external CMS remains
an appropriate dynamic extension point; built-in kernels need not use its
object interface.

Preserve the deliberately open `Pixel` trait for custom pixel implementations.
Seal new implementation-only extension points from their first release when
appropriate. Retrofitting sealing or exhaustiveness restrictions onto exchanged
types conflicts with a compatibility promise even if a local grep finds no
victims.

## 3. Correctness with bounded overhead

**Validate at boundaries, then execute using established invariants.** Check
geometry, overflow, minimum backing extent, channel alignment and typed layout
at construction/adoption. Check replacement planes when they are installed.
Mutation of samples should not allow mutation of the storage topology.

A writable legacy descriptor remains an unvalidated description. The planner
can hold a private validated representation while the 0.4 descriptor contract
is developed with its concrete cross-crate consumers. Legacy buffer methods
cannot make every possible legacy value trustworthy. New execution entry
points must validate what their legacy inputs do not prove.

Resolve ICC/CICP conflicts, sample range, alpha convention and HDR luminance
anchor during preparation. Unknown remains unknown unless the caller supplies
an explicit assumption. Retagging changes metadata; conversion changes samples.
Neither should silently masquerade as the other. Emitted metadata must describe
the resulting pixels, including when the target says “same as origin.”

Separate three questions: can the operation execute, what does it preserve,
and which permitted alternative is preferable? A heuristic loss score of zero
does not establish exact sample preservation. Codec acceptance and encoded
preservation belong to zencodec/codec implementations, not the interchange
crate. Keep perceptual ranking and backend feasibility out of core.

Make the performance promises concrete:

| Operation | Target contract |
|---|---|
| Borrow an existing buffer or crop a view | No pixel allocation/copy; no atomic refcount operation on the ordinary borrowed-context path |
| Borrow-or-own identity adaptation | Return the original storage with consistent interpretation |
| Move a buffer between supported version facades | The same Rust type; no conversion, allocation, or dispatch |
| Prepare conversion for a known width | Validate semantics, choose kernels, reserve scratch, initialize required backend/LUT state |
| Execute prepared conversion | No allocation for the prepared capacity; no internal mutex for worker-owned CMS state; no per-pixel policy/CPU dispatch |
| Change width beyond capacity | Explicit preparation/growth or a documented failure; no surprise allocation under a strict no-allocation contract |
| Fork execution onto another thread | Create independent mutable state or report that the backend cannot do so |
| Compose plans | Preserve quantization, clipping and CMS effects; refuse unsupported composition |

“No runtime overhead” should mean no avoidable framework work beyond the
requested operation. Untrusted dimensions still require validation, conversion
still costs computation, and an optional dynamic CMS requires dispatch. Measure
per-row overhead against invoking the same selected kernel directly. A
function pointer is a reasonable candidate, not an automatic speed win over a
small enum match. Benchmark both where it matters.

Borrowed metadata can be introduced with private borrowed/owned context storage
inside existing lifetime-bearing views, preserving owned attachment methods.
That design needs size and branch-cost measurements: an enum may grow the view.
Do not promise that the current `PixelSlice` becomes `Copy`; its public API also
supports independently owned metadata. If a smaller borrowed view is needed,
demonstrate a real caller before adding another public carrier.

## 4. Compile-time evidence and priorities

Isolated external consumers were built with `cargo build --offline --timings
-j 4`, each in a fresh target directory, using a copy of this checkout's lock
file. No crate tests, dev-dependencies, ICC generator or apidoc tooling were
built. Environment: Ryzen 9 9950X3D, rustc 1.98.1, x86_64 Linux, dev profile;
no RUSTFLAGS or compiler wrapper environment variables. Package downloads and
filesystem caches were warm. These are single diagnostic runs, not statistical
benchmarks or estimates of release-code generation.

| Consumer | Wall time | Selected Cargo compilation units |
|---|---:|---|
| Core, default features | 1.76 s | syn 3: 0.69 s; bytemuck_derive: 0.31 s; zenpixels: 0.27 s |
| Core, no default features | 1.51 s | syn 3: 0.63 s; bytemuck_derive: 0.29 s; zenpixels: 0.24 s |
| Convert, default features | 4.59 s | convert: 1.22 s; magetypes: 1.18 s; syn 2: 1.09 s; syn 3: 0.68 s |

Compilation units overlap; their durations must not be summed as wall time.
Within one Cargo build, dependencies are shared where resolution and build
configuration permit. Hundreds of consumers do not each pay another complete
core build. Duplicate versions, separate targets and generic instantiations
are more useful things to investigate than multiplying these times by crate count.

Priorities:

- Preserve the light core boundary and independently version conversion.
- Keep a single compiled implementation behind compatible core facades.
- Investigate the five POD derives. They account for most of the core's
  observed compilation chain. Handwritten unsafe Pod impls would violate the
  present `forbid(unsafe_code)` policy. A tiny audited leaf with a deliberate
  policy change is one possible tradeoff; improving the upstream derive path
  is another. Neither is implemented or assumed here. Moving unchanged derives
  into another crate alone does not remove their cold compilation cost.
- The current convert graph contains syn 2 through archmage-macros and syn 3
  through bytemuck_derive. Align upstream macro dependencies when supported;
  do not force an incompatible dependency version to make the tree look smaller.
- Avoid broad inlining and type-level color/backend combinations. Use real
  consumer build timings before splitting more crates or adding a feature matrix.
- Keep CMS integration, profile database and optional interoperability costs
  explicit. Disabling CLL does not remove the unconditional SIMD dependencies.

Keep whereat for now. In an isolated size probe, `PixelDescriptor` was 5 bytes,
`PixelSlice` 48, `PixelBuffer` 64, `BufferError` 1, and `At<BufferError>` 16.
Both plain-error and traced-error `Result<PixelSlice, _>` were 48 bytes.
This is configuration-specific layout evidence, not an ABI promise or a runtime
benchmark. It provides no reason to break every error signature to chase an
assumed large success-path overhead.

Further performance gates should cover cold dev and release builds, incremental
consumer edits, minimal/full features, runtime allocations and default-target
x86/ARM conversion throughput. Set numerical regression budgets after repeated
baselines on controlled runners. Do not invent a universal millisecond target
from one workstation run.

## 5. What “compatible with 0.2–0.4” can mean

| Guarantee | What actually establishes it |
|---|---|
| The same source builds with any supported release line | A common API and feature contract, tested against each selected version |
| Different release lines exchange buffers in one process | Re-exported types from one defining package, or explicit adapters |
| An old locked binary/source build upgrades without work | Only if its constraints permit the bridge update; immutable historical packages cannot be retrofitted |
| The same pixels retain the same meaning | Behavioral conformance, beyond compilation and deprecation checks |

Cargo can select separate pre-1.0 minor versions, including when a broad range
overlaps a narrower requirement. Independently defined types remain distinct.
Its documented semver-trick remedy is re-exporting types from one version into
another. See [Cargo dependency resolution](https://doc.rust-lang.org/cargo/reference/resolver.html#version-incompatibility-hazards)
and the [original semver-trick explanation](https://github.com/dtolnay/semver-trick).

This is already relevant: zencodec requests `0.2.14`, while zenpixels-convert
requests `>=0.2.16, <0.4.0`; several sampled codecs use similarly wide ranges.
Those requirements can admit different core minor versions. None of the sampled
wide requirements admits 0.4 today. Current public signatures in zencodec,
zenresize and zenpipe expose the pixel carriers directly.

### Mechanism for retaining the existing type surface across all three lines

This option preserves today's carrier API and was the initial recommendation.
Following the owner clarification, prefer the coordinated redesign and additive
common migration surface in section 0. The mechanism here applies to unchanged
types, or where preserving an existing type is an intentional design choice.

Introduce one stable defining package, provisionally `zenpixels-types` on a
stable version line. It owns the exchanged types **and their required trait
implementations**, with no dependency back to a facade. Treat 1.0 for that
package as a real stability commitment; choose its initial release only after
the surface audit. It is an implementation-sharing boundary, not a second
user-facing API callers must learn.

```text
zenpixels 0.2.B ─┐
zenpixels 0.3.C ─┼── re-export ──> one zenpixels-types definition
zenpixels 0.4.x ─┘                         ↑
                               conversion and codec boundaries
```

`B` and `C` are the first bridge patches, not chosen release numbers. If 0.3.1
is still unpublished, make its initial release a bridge rather than creating
another independent type universe. Production facades preserve existing module
paths, feature forwarding and documented imports; they need not expose an
unreviewed blanket glob.

Share the closure of the API: buffers/views/cow, descriptors and their enums,
color/HDR/planar carriers, `Pixel`, errors and any traits used to exchange them.
Sharing only `PixelDescriptor` leaves the most important boundary broken.
Preserve compatible identities of exposed third-party types too: `rgb`,
bytemuck trait bounds, and whereat error wrappers. Avoid exact pins or source
overrides that produce incompatible defining packages.

Inherent implementations and foreign-trait implementations involving the moved
types must live where Rust's coherence rules permit them, normally the defining
package. A facade cannot attach its own inherent methods to a re-exported type.
Existing public dependencies and macros require a packaging/coherence audit;
the prototype below does not replace it.

**The unavoidable constraint:** one type has one public shape and method set.
We cannot keep `into_vec` on the 0.2 version of a shared `PixelBuffer` while
removing that inherent method from the 0.4 view of the same type. Nor can we
make shared public fields private only in 0.4. If choosing this option, keep
deprecated members on shared types and guide new code away from them. A
redesigned carrier is a new type with an explicit bridge; it can be re-exported
through new paths on older lines without retaining every legacy member.

This changes the old removal-driven release plan. A universal “warning-free on
0.2 means builds on 0.4” claim is stronger than that plan can establish:
exhaustiveness, trait implementations, feature selection, MSRV and semantic
changes do not all produce deprecation warnings.

### Evidence from a local prototype

Copied the actual current core sources into a temporary defining package and
built three thin packages named `zenpixels`, with experimental versions 0.2.99,
0.3.99 and 0.4.0. One consumer depended on all three simultaneously.

The compiled and executed probe passed:

- A buffer constructed through 0.2 passed directly through functions accepting
  0.3 and 0.4 buffers, with the pixel pointer unchanged.
- Its color-context Arc retained the same pointer.
- A typed `PixelSlice<Rgbx>` crossed the same boundary.
- A 0.2 `Rgbx` satisfied the 0.4 `Pixel` bound.
- A 0.2 `BufferError` assigned directly to the 0.4 error type.

This establishes the mechanism with real carrier implementations. It does not
establish compatibility of a redesigned 0.4 implementation, all feature sets,
MSRV, published packaging, every macro, or all consumers. These experimental
versions were not published and do not represent actual release artifacts.

### Alternatives and limits

The simplest option is to keep core on 0.2 with additive evolution and advance
zenpixels-convert to 0.4 independently. The packages already release
independently. Choose this if there is no material reason to release three core
lines: it avoids a new defining package entirely.

The conventional semver trick makes old facades depend on the newest core
directly. It avoids a new package, but then the newest core must preserve every
shared legacy member and the old lines inherit its dependency/MSRV floor.
A separate stable defining package is preferable if facade and engine evolution
must remain independent over several future releases.

Separate old/new carriers plus adapters permit genuine redesign, but require
call-site adaptation and are not identical types. Borrowed adapters may avoid
copying pixels; owned adapters need complete layout/offset/context extraction
to avoid copying or losing semantics. `repr(C)`, matching struct definitions,
newtype wrappers and `From` implementations do not establish Rust type identity.

Exact `=0.2.16` dependencies and lockfiles retaining pre-bridge artifacts remain
outside automatic interoperability. They need an allowed dependency update or
an explicit boundary adapter. Yanking does not rewrite an existing artifact or
lockfile. No release architecture can retroactively change those definitions.

## 6. Consumer manifests and release sequence

With shared identities, consumers usually do **not** need a cross-minor range:
an older codec can request the 0.2 bridge line and a newer codec 0.4; their
buffers still interoperate. Conservative requirements are easier to reason
about than teaching every leaf to select among three API versions.

A consumer intentionally supporting every line may use a range such as
`>=0.2.B, <0.5.0` only after its common API/feature subset is tested. The notation
is schematic, not valid TOML until B is replaced. It also admits every 0.3
release in that interval: ensure they all implement the contract. Cargo's
comma-separated comparisons are conjunctions, not an OR of separately bounded
release families; see [specifying dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#multiple-version-requirements).

New APIs require a minimum bridge patch containing them. Do not advertise
support back to 0.2.10 just because the manifest accepts it. Pin the selected
version in each CI fixture; a normal update otherwise tends to test only the
newest allowed release. Local path dependencies do not exercise release-line
selection adequately.

Revised proposed sequence:

1. **Current-line correctness:** fix the reproduced pixel, storage, metadata
   and plan defects with behavioral regressions. Distinguish bug repair from
   deliberate semantic changes; make newly rejected operations explicit in
   release notes. Do not freeze those defects into a stable contract.
2. **Design the destination with real consumers:** settle checked storage,
   borrowed metadata, color authority, complete plans, output ownership and
   worker semantics together. Exercise zencodec and representative codecs before
   freezing names and signatures. Remove ambiguous contracts where the new
   design provides a complete replacement.
3. **Build the common migration surface:** distinguish unchanged types eligible
   for direct re-export from redesigned types requiring new additive paths in
   old releases. Choose one owner for the new definitions and an acyclic
   package graph. Preserve core's 1.85 MSRV and no_std+alloc capability unless a
   deliberate separately assessed change is necessary; conversion currently
   has a separate 1.89 floor. Test the real dependency closure.
4. **Migrate the controlled ecosystem:** update shared integration APIs first,
   then codecs, processing libraries and applications. Compile migrated source
   against each supported bridge line and 0.4. Version changed downstream
   public signatures appropriately. Direct unpublished crates to the new API.
5. **Package destination and bridge releases:** publish defining packages before
   the facades that depend on them, then migrated downstream packages. Keep
   legacy compatibility in the old lines when it obstructs the new contracts.
   Feature unification must not switch type definitions or correctness
   semantics. Align public CMS/plan identities where consumers exchange them;
   core identity alone does not unify independently defined converter types.
6. **Release gates:** validate packaged artifacts and published older consumers,
   then publish and widen requirements only for demonstrated compatibility.

Required compatibility matrix:

- Same consumer source against minimum bridge and latest supported patches of
  0.2, 0.3 and 0.4, with deprecations denied on the preferred API fixture.
- One mixed-version executable passing owned, borrowed, mutable, typed, planar,
  color and error values through representative codec boundaries.
- Feature combinations: minimal external consumer, defaults, rgb/imgref,
  planar, ICC; conversion with/without CMS and HDR; no_std and MSRV.
- Published older converter against each new admitted core version, rather
  than rebuilding a simultaneously edited workspace only.
- Package/module/re-export/coherence and semver checks; assess every failure.
- Semantic comparisons of bytes AND interpretation, alpha/range, ICC/CICP,
  luminance anchor, layout and metadata retention. Include unsupported-path
  refusals, saturated color fixtures and independent HDR reference values.
- Allocation and throughput gates for identity, prepared rows, ownership
  transfer and CMS execution. Distinguish first-use setup from steady state.

Keep the scope in zenpixels proportionate: zencodec negotiation and preservation
need integration work, but codec policy, EXIF rewriting and every HDR algorithm
do not belong in the core crate or need to block its compatibility bridge.
