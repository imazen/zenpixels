Every valid native pixel pair already runs in one compact universal scalar loop (UniversalPlan). So why does zenpixels-convert ship over 100 specialized steps and SIMD kernels? The 5 reasons kernel count multiplies

1. Byte layout × lane width

3bpp (RGB), 4bpp (RGBA/BGRA), 2bpp (GrayAlpha), and 1/2/4-byte samples each require completely different SIMD shuffle/deinterleave masks — and splitting per-type avoids cross-product codegen bloat.

2. Peephole fusion (1 RAM pass vs 3)

Converting P3 RGB8 → sRGB RGB8 step-by-step touches RAM 3× (decode → 3×3 matrix → encode). Fused FusedKind kernels keep intermediates in registers — 3–7× faster.

3. Transfer × Clip vs Extended × Truncate

Clamped [0,1] sRGB/Gamma22, sign-reflected PreserveExtended, DepthPolicy::Round vs Truncate, and alpha-preserving RGBA all differ at boundary bits — zero tolerance for 1-bit drift.

4. FloatFacts & const magemath

Clean unit-bounded floats elide per-pixel NaN/Inf/subnormal branches in Oklab, BT.709, Gamma 2.2, and float quantization — gaining 1.3–15× without breaking untrusted inputs.

5. Fast transposes & fused scans

In-register 8×8 / 16×16 transposes for 1/2/3/4/6/8/12/16-byte pixels (EXIF orientation) plus read-only SIMD scans (opaque / grayscale / U16 bit-replication) for lossless codec negotiation.
