Why pixel codes are curved, not linear

Human eyes see brightness roughly logarithmically: a tiny step near black looks as big as a huge jump near white. Transfer functions bend stored codes to match human vision (and HDR headroom). Hover the charts to inspect exact EOTF/OETF values, compare bit allocation, and generate live zenpixels-convert Rust code below.

02

HLG on the Web & why a 1D curve isn't enough

Unlike PQ (where every code has one absolute brightness in nits), HLG is display-adaptive and channel-coupled. Two rules explain almost every HLG surprise on the web:

HLG on the web (Chrome, Safari, CSS HDR & ICC): Browsers and OS compositors render HLG using the viewer's live display peak Lw, black floor Lb, and surround-adjusted γ — so the exact same HLG image maps 75% signal to ~203 nits on a 1000-nit reference monitor, ~81 nits on a 300-nit SDR laptop, and ~342 nits on a 2000-nit TV. Because the BT.2100-3 OOTF scales all three channels by shared BT.2020 luminance Ysγ−1 (not independent per-channel cγ), standard 1D ICC TRCs cannot represent HLG display rendering — which is why zenpixels requires explicit HlgRendering (on full-range BT.2020 RGB/RGBA) and refuses HLG ICC synthesis.
