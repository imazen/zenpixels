# RGB16 narrowing audit — 2026-09-23

## Result and scope

The requested failing same-transfer test on `main@origin` could not be reproduced. The base commit `e56f626b` already contains the exact integer narrowing fix from `1eb8c9b8`. The published `zenpixels-convert` 0.2.16 used by zenmetrics predates it. This lane adds a public-entry regression test and fixes a second, distinct precision issue found by the transfer-pair audit.

## Defect and localisation

The published 0.2.16 `ConvertStep::U16ToU8` called `garb::bytes::convert_u16_to_u8` in `src/convert_kernels.rs` (registry source line 1724). Its arithmetic `(v*255+32768)>>16` divides by 65536 and differs from exact `(v*255+32767)/65535` on 127 of 65,536 codes; the first is 33025, where it emits 128 instead of 129. The current source's `u16_to_u8` in `zenpixels-convert/src/convert_kernels.rs` uses a byte-lane correction and the same-transfer planner in `src/convert.rs` chooses `U16ToU8`. The `__trace_ops` test records that selected step for tagged sRGB.

The real-transfer defect was in `depth_steps` in `src/convert.rs`: it used `U16ToF32` → f32 EOTF/OETF → `NaiveF32ToU8`. Instrumented exhaustive outputs differed from the continuous transfer definitions evaluated in f64 in every tested SDR transfer pair (9 to 90 codes); a separate 40-digit decimal evaluation confirmed the results. A private `SdrU16ToU8` step now builds one 65,536-entry u8 table lazily for each of the six Linear, BT.709 and sRGB transfer pairs, composing in f64 and quantising once when the table is built. It is selected only for matching primaries. Alpha is narrowed as a linear channel. Same-transfer code stays on the exact integer step. No public API was added.

## Routes audited

| Source → target | Planner/kernel | Coverage |
|---|---|---|
| u16 → u8, same transfer and primaries | `U16ToU8`; all RGB/RGBA/gray/gray-alpha formats | Exhaustive new test, including straight and premultiplied alpha and strided rows |
| u16 → f32 → u8, same transfer | `U16ToF32` then `NaiveF32ToU8` | Exhaustive new parity test for the same layouts and transfers |
| f32 → u8, same transfer | `NaiveF32ToU8` | Covered above for f32 values representing every u16 code |
| u16 → u8, differing Linear/BT.709/sRGB transfer, same primaries | `SdrU16ToU8` lazy f64-composite LUT | Exhaustive six-pair f64 oracle; zero mismatches after fix |
| f32 Linear → u8 sRGB | `LinearF32ToSrgbU8` | Existing transfer tests; high-precision exhaustive oracle pending |
| PQ/HLG u16 → u8 sRGB | HDR EOTF and sRGB output kernel | Existing HDR tests; outside the SDR rounding oracle |
| differing primaries | CMS or gamut path | Outside exact integer narrowing; no relabeling assumed |

The new test enumerates Linear, BT.709 and sRGB transfers. It checks no alpha mode, straight alpha, and premultiplied alpha where the layout supports it.
The integer narrowing loop itself has no archmage-token dispatch; the forced-tier test runs the public converter under each available token permutation and confirms that surrounding dispatch does not alter its bytes.

The optional x86 narrowing follow-up was checked arithmetically: `(v*255 + 32895) >> 16` equals `(v*255 + 32767) / 65535` for all 65,536 u16 codes. The existing exact byte-lane kernel is slower than the prior inexact garb kernel on this x86 host in the contended run below. A new explicit SIMD dispatch and tier proof are outside this correction; this formula is a candidate for that separate work.

### Performance, CONTENDED

The four-size zenbench run ended successfully but reported **one measurement round per size** and **112 noisy rounds** on the shared host. These figures are descriptive only; they cannot support a reliable speedup claim. The before arm is the old, inexact `garb` kernel; the after arms are the exact byte-lane kernel and shipped `RowConverter`. Units are mean time per RGB image row containing `3×pixels` samples.

| Pixels | garb old | exact byte lanes | shipped converter |
|---:|---:|---:|---:|
| 64² | 850 ns | 4,423 ns | 4,447 ns |
| 256² | 12.4 µs | 71.1 µs | 70.9 µs |
| 1024² | 212.0 µs | 1,156.5 µs | 1,143.8 µs |
| 4096² | 4.0 ms | 18.2 ms | 18.2 ms |

Unweighted least-squares `T(ns)=α+β·pixels`, fit to the displayed rounded means: old `α=-13,539.9 ns`, `β=0.239134 ns/pixel`; byte lanes `α=6,182.8 ns`, `β=1.084483 ns/pixel`; shipped `α=1,985.7 ns`, `β=1.084702 ns/pixel`. The negative old intercept and one-round samples underline the measurement limitation.

### Real-transfer LUT A/B, CONTENDED

The second zenbench compares the former `U16ToF32` → f32 transfer → `NaiveF32ToU8` sequence with the new direct LUT step. Each arm converts a caller-owned tight RGB row; the LUT is initialized before timing. Each size received one round and the run reported 224 noisy rounds, so the figures are indicative. Units are time per `pixels×3` samples.

| Pixels | BT.709→sRGB old f32 | BT.709→sRGB LUT | Linear→sRGB old f32 | Linear→sRGB LUT |
|---:|---:|---:|---:|---:|
| 64² | 18.2 µs | 4.6 µs | 3.6 µs | 4.6 µs |
| 256² | 286.7 µs | 75.4 µs | 59.1 µs | 75.7 µs |
| 1024² | 5.3 ms | 1.4 ms | 1.0 ms | 1.3 ms |
| 4096² | 87.8 ms | 22.2 ms | 19.9 ms | 22.1 ms |

Unweighted least-squares `T(ns)=α+β·pixels` fits to those displayed means: BT.709→sRGB old `α=-81,738.2`, `β=5.237755`; LUT `α=-147.1`, `β=1.323276`. Linear→sRGB old `α=-86,293.9`, `β=1.190689`; LUT `α=-30,430.1`, `β=1.318886`. The BT.709 route is about 4× faster at 4096², while the Linear route is about 11% slower at that size. Input-byte throughput for the LUT is 4.20 and 4.65 GiB/s at 1024² for BT.709 and Linear respectively; the planner estimate is rounded down to 4.0 GiB/s. The negative intercepts and single rounds prohibit a stronger speed claim.
